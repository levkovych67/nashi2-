## 1. Навіщо

Нова версія «Наших» зі зручним mobile-first інтерфейсом. Фаза 1 дає змогу знаходити музикантів за місцем
походження на карті України, слухати випадкові фрагменти їхніх творів, переглядати сторінки музикантів, ставити
лайки і пропонувати нових музикантів через форму з модерацією в Telegram-групі.

## 2. Архітектура (коротко)

```
                 ┌────────────── браузер (телефон / desktop) ──────────────┐
                 │  web: React SPA                                          │
                 │   core/ (headless: карта, аудіо, лайки, форма, фільтри)  │
                 │   ui/   (скін; замінюється після handoff від студії)     │
                 └───────┬──────────────────────────────┬───────────────────┘
                         │ /api/v2 (JSON, multipart)     │ тайли карти, прев'ю аудіо, фото Commons
                 ┌───────▼────────┐               ┌──────▼──────────────────────────┐
                 │ nginx (TLS)    │               │ OpenFreeMap/MapTiler, Deezer,   │
                 └───────┬────────┘               │ iTunes, Wikimedia (зовнішні)    │
                 ┌───────▼──────────────────────────────────────┐
                 │ backend: Spring Boot (Java 21)               │
                 │  map · artist · place · like · submission    │──── S3 (фото, завантажене аудіо)
                 │  moderation · telegram · wiki · audio · jobs │──── Telegram Bot API (група модерації)
                 └───────┬──────────────────────────────────────┘──── Wikidata / uk.wikipedia / Commons / MusicBrainz
                 ┌───────▼────────┐
                 │ MongoDB 8      │  artists · places · submissions · jobs_runs
                 └────────────────┘
```

Ключові принципи: contract-first (`contracts/openapi.yaml`); headless-логіка відокремлена від скіну, тому
затверджений дизайн підключається без зміни backend і логіки; повторне використання перевірених частин V1
(імпорт з Вікіпедії, guard секретів, правила карти).

## 3. Функціональні вимоги

### Карта
- **FR-01** Інтерактивна карта України на весь екран; mobile і desktop; масштабування жестами, колесом і кнопками; межі — Україна (з Кримом).
- **FR-02** Початковий вигляд — уся Україна; область за посиланням `/?region=<CODE>`; кнопка «Біля мене» (D-10).
- **FR-03** Кількість музикантів: на дрібному масштабі — по областях, на середньому — по населених пунктах, на великому — окремі піни (D-12; пороги — конфігурація).
- **FR-04** Тап/клік по області чи пункту — плавне переміщення до центральної частини території (D-17).
- **FR-05** Піни прив'язані до місця народження/заснування; якщо відоме лише місто походження — детермінована випадкова точка в межах міста, збережена в БД (D-13, формула — контракти §4).
- **FR-06** Постійне пояснення: «Позначка — місце походження музиканта, а не те, де він зараз» (D-14) — на карті, у картці, на сторінці.
- **FR-07** Фільтр за областю (мультивибір, стан у URL, кількість результатів); структура критеріїв розширювана через `GET /api/v2/filters`.

### Аудіо
- **FR-10** Взаємодія з піном запускає випадковий фрагмент одного з творів музиканта (15 с, D-21).
- **FR-11** Desktop — наведення з затримкою наміру 250 мс; зупинка при знятті наведення (D-22, D-26).
- **FR-12** Mobile — режим, затверджений дизайном (`audio.mobile-trigger`); до затвердження — `TAP_PREVIEW_AND_PLAY`; усі три режими D-25 перемикаються конфігурацією.
- **FR-13** Одночасно грає не більше одного фрагмента; обробка блокування автоплею (D-23); на iOS без fade (D-24).
- **FR-14** Джерела фрагментів: UPLOAD, DEEZER, ITUNES, COMMONS (D-20) через розширюваний інтерфейс провайдерів; фоновий пошук аудіо для музикантів без нього; звіт покриття.

### Музикант
- **FR-20** Окрема сторінка `/m/<slug>`: ім'я/назва, короткий опис, зображення, музичні матеріали (кліпи, твори, відео), посилання на музику, YouTube-канал, місце походження, кнопка лайку, загальна кількість лайків; атрибуція Вікіпедії й авторів фото.
- **FR-21** Картка-прев'ю з карти з переходом на сторінку; відкриття музиканта на карті за посиланням.

### Лайки
- **FR-30** Лайк без реєстрації і верифікації; необмежено; кожен тап +1; лічильник оновлюється миттєво (D-30, D-31).
- **FR-31** Сервер атомарно збільшує лічильник; обмежується лише частота запитів (D-32).

### Вікіпедія
- **FR-40** Parser отримує з Вікіданих/Вікіпедії дані про музикантів (D-51) і записує їх у модель; щомісячний запуск і команда в Telegram; без дублікатів; правила виключення V1 (D-50).
- **FR-41** Короткий опис очищений від артефактів; атрибуція CC BY-SA поруч з текстом.

### Пропозиція і модерація
- **FR-50** Форма пропозиції: дані, посилання, 1–5 фото (контракти 2.10); автодоповнення населеного пункту; стиснення фото на телефоні; зрозумілі помилки; захист від спаму (D-46).
- **FR-51** Заявка надходить у Telegram-групу адміністраторів, налаштовану конфігурацією (chat id групи, опційно тема форуму), а не один administrator ID.
- **FR-52** «✅ Так» — схвалити, «❌ Ні» — відхилити; хто може натискати — `approver-policy`; повторні натискання і гонки між адміністраторами безпечні; повідомлення оновлюється підсумком.
- **FR-53** Після «Так» музикант публікується автоматично (D-43) і з'являється на карті; після «Ні» — не публікується; заявка і журнал дій зберігаються (D-44).
- **FR-54** Команди групи: `/hide`, `/show`, `/stats`, `/wiki_import`, `/audio_resolve`.

### Дані і перехід
- **FR-60** Довідник населених пунктів України (≥ 25 тис., з Вікіданих) для автодоповнення, агрегації і розміщення пінів.
- **FR-61** Міграція музикантів з V1 (з фото і демо-треками) — ідемпотентна команда (D-69).

### Інтеграція з дизайном
- **FR-70** API і модель даних готові до підключення затвердженого UI: контракт `contracts/openapi.yaml`, токени дизайну `--n-*`, `decisions.json` як конфігурація варіантів.
- **FR-71** Підключення handoff від студії (`npm run design:sync -w web`) змінює лише `web/src/ui/` і `web/src/design/`; тести `web/src/core/` і backend лишаються без змін і зеленими.

## 5. Критерії приймання

Від замовника (протокол) → де перевіряється (детальна матриця — у плані):
- [ ] «Наші V1» проаналізовано, а повторно використані технології та компоненти задокументовано → `docs/00-v1-audit.md`.
- [ ] Система відкривається й коректно працює на мобільному та desktop-екрані → E2E Playwright (iPhone 13, Desktop 1440).
- [ ] На карті відображається Україна або визначений початковий регіон → E2E: `/` і `/?region=LVIV`.
- [ ] Карта підтримує плавне переміщення та масштабування → E2E + ручна перевірка.
- [ ] Для міста або регіону відображається кількість пов'язаних із ним музикантів → unit-тести рівнів агрегації + E2E.
- [ ] Після збільшення масштабу користувач бачить pin-маркери окремих музикантів → E2E.
- [ ] За наявності точних даних pin-маркер відповідає місцю народження музиканта → unit-тест `PinPlacer` (EXACT/SETTLEMENT).
- [ ] За відсутності точних даних pin-маркер розташовується в межах відповідного міста походження → unit-тест (відстань ≤ R, стабільність).
- [ ] Біля карти постійно доступне пояснення про геомітку → E2E: елемент видимий на всіх рівнях масштабу і при відкритій картці.
- [ ] Під час визначеної взаємодії з pin-маркером запускається випадковий фрагмент твору відповідного музиканта → unit-тести аудіо-двигуна і `FragmentService` + E2E.
- [ ] Кожен музикант має окрему сторінку з описом, зображеннями, музичними матеріалами та посиланнями → E2E на фікстурах і на staging.
- [ ] Parser отримує доступні дані про музикантів із Wikipedia та передає їх у структуру системи → unit-тести на записаних відповідях API + звіт першого імпорту.
- [ ] Користувач може відфільтрувати музикантів за областю → E2E.
- [ ] Користувач може поставити одному музиканту необмежену кількість лайків без реєстрації та верифікації → E2E (100 тапів = +100).
- [ ] Після кожного лайку загальний лічильник музиканта збільшується на один → інтеграційний тест `$inc` + UI.
- [ ] Форма пропозиції музиканта приймає дані, посилання та зображення → інтеграційний тест multipart + E2E.
- [ ] Після надсилання форми заявка надходить у визначену Telegram-групу адміністраторів → тест з підробленим TelegramClient + ручна перевірка на staging-групі.
- [ ] Адміністратор може схвалити заявку дією «Так» або відхилити дією «Ні» → тести callback-обробника.
- [ ] Відхилена заявка не публікується в системі → інтеграційний тест.
- [ ] Технічна реалізація дає змогу підключити затверджений дизайн без перероблення основної backend-логіки → FR-71: diff підключення handoff не торкається `backend/` і `web/src/core/`.

## 6. Відповіді на «Питання до виконавця»

| Питання | Відповідь (детально — у плані) |
|---|---|
| Технічний аудит V1 і повторне використання стеку | `docs/00-v1-audit.md`: беремо MongoDB, імпорт з Вікіпедії, guard секретів, S3, стек фронтенду, правила карти; прибираємо AI, події, новини, радіо; замінюємо модерацію, деплой, контракт API |
| Етапи, терміни, вартість | ≈ 10–11 тижнів; етапи і людино-дні за ролями — план, розділ «Оцінка». Вартість = людино-дні × ставки |
| Агрегування пінів і кількостей на різних масштабах | Три рівні (D-12): області (`/map/regions`) → населені пункти (`/map/places`, близькі об'єднуються supercluster-ом) → піни (`/map/pins`, supercluster для щільних місць). Усе на клієнті: ≈ 3,7 тис. пінів ≈ 90 КБ gzip. При > 50 тис. — перехід на серверну кластеризацію за bbox або векторні тайли (PMTiles) без зміни UI |
| Механізм випадкових фрагментів | Бекенд обирає випадковий кліп і старт (`GET /musicians/{id}/fragment`), видає свіжий URL прев'ю; клієнт має один спільний аудіо-елемент, hover-intent на desktop, стратегію тригера на mobile, fade де дозволяє браузер. Джерела — провайдери UPLOAD/DEEZER/ITUNES/COMMONS (D-20) |
| Технічні й правові обмеження Вікіпедії | Лише офіційні API; User-Agent, послідовні запити, `Retry-After` (досвід V1: повний імпорт ≈ 6 год); тексти — CC BY-SA 4.0 з атрибуцією і тією ж ліцензією для похідного опису; Вікідані — CC0; фото — ліцензія кожного файла з показом автора (D-52) |
| Модель модерації через Telegram-групу | Заявка → альбом фото + картка з кнопками «Так/Ні» у групі; право натискати — адміни групи (або всі учасники); атомарний перехід статусу, перший клік виграє; повідомлення редагується з підсумком; історія в `submissions.moderationLog`; команди `/hide`, `/show` для виправлень (D-42–D-47) |
| Які API-контракти погодити з дизайном до затвердження UI | Форма піна (`MapPin`: які поля видно на піні), кількості (`RegionStat`, `PlaceStat`), картка і сторінка (`MusicianDetails`), фрагмент (`Fragment`: тривалість, fade, атрибуція), лайки (батчинг), фільтри (`FilterDefinition`), форма (поля і ліміти 2.10), помилки (Problem Details), токени (контракти §5), тексти (§8), рішення (§6–7). Усе вже зафіксовано в `02-contracts.md` |

## 7. Залежності

- Доступи (`01-decisions.md`, розділ I): Telegram-група і новий бот, MongoDB і S3 V1 (для міграції), VPS, домен, (опційно) MapTiler, ключ YouTube Data API (для відео).
- Юридичне підтвердження прев'ю Deezer/Apple — до публічного запуску (до того фрагменти лише з UPLOAD і COMMONS).
- Пакет handoff від студії — для задачі «імплементація затвердженого дизайну» (до того — каркасний UI на тих самих компонентах логіки).

## 8. Не входить

Поети, архітектори та інші види мистецтва; адмін-панель у браузері; повідомлення заявникам; реєстрація
користувачів; пости в публічний Telegram-канал; англійська версія.

## 9. Ризики

| Ризик | Вплив | Що робимо |
|---|---|---|
| Мало музикантів зі звуком | Головна «фішка» карти слабка | Кілька провайдерів, міграція демо-треків V1, Commons для історичних постатей, команда `/audio_resolve`, звіт покриття; дизайн стану «без звуку» |
| Умови Deezer/Apple не дозволять прев'ю | Втрачаємо ≈ 10 % звуку | Провайдери вимикаються конфігурацією; UPLOAD і COMMONS лишаються |
| Накрутка лайків | Рейтинг недостовірний | Свідоме рішення замовника (D-30); обмеження частоти; журнал аномалій — фаза 2 |
| Затримка handoff від студії | Зсув запуску | Каркасний UI на тій самій логіці; handoff — окрема задача в кінці |
| Довгий повний імпорт (≈ 6 год у V1) | Рестарт посеред імпорту | Імпорт ідемпотентний і продовжується з місця зупинки; деплой не під час імпорту |
| Spring Boot 4 і бібліотеки | Несумісність | Перевірка в першій задачі; запасний варіант 3.5.x (D-61) |
