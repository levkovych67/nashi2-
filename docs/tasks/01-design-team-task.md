## 1. Навіщо

До остаточної імплементації треба погодити повний UX, айдентику і візуальну систему «Наші V2». Замовник має
**побачити й відчути** варіанти — передусім на власному телефоні — порівняти їх і зафіксувати вибір по кожній
складовій. Обраний набір передається технічній команді як пакет, за яким продукт збирається без повторного
узгодження базових сценаріїв.

## 2. Що таке студія

Окремий вебзастосунок (не Figma-файл). Figma лишається робочим інструментом дизайнерів; студія — місце, де
варіанти **живі**: справжня карта України (MapLibre), реальні музиканти з Вікіпедії (≈ 4,3 тис. з даних V1),
звук, жести, анімації, мобільні й desktop-екрани.

Студія вміє:
1. Показати каталог рішень (`02-contracts.md`, розділ 6) зі статусом кожного: «немає вибору» / «запропоновано» / «затверджено».
2. Порівняти 2–4 варіанти одного рішення поруч у рамках телефона (390×844) і desktop (1440×900), з описом, плюсами і мінусами.
3. Відкрити будь-який варіант на весь екран **на телефоні замовника** (QR-код на сторінці порівняння).
4. Перемикати айдентику: будь-який варіант UX показується в будь-якому напрямі айдентики.
5. Пройти наскрізний сценарій («від карти до музиканта», «запропонувати музиканта»), зібраний з поточного вибору.
6. Зафіксувати вибір: чернетка → посилання для команди → затвердження дизайн-лідом у git.
7. Згенерувати пакет handoff для технічної команди (`02-contracts.md`, розділ 7).

## 3. Обсяг

### Входить
- Аналіз дизайну, структури та UX V1 (розділ у студії `/audit`; база — `00-v1-audit.md`, розділ 6).
- Айдентика: **3 нові напрями** + V1 (Frutiger Aero) як точка відліку. Кожен напрям: логотип «Наші» (повний і знак),
  палітра, шрифти з кирилицею і вебліцензією, іконки, тон текстів, стиль базової карти, усі токени розділу 5 контрактів.
- Варіанти кожного UX-рішення з каталогу (по 2–4), див. розділ 4.
- Наскрізні сценарії на mobile і desktop.
- Тексти інтерфейсу за замовчуванням (`copy.uk.json`), включно з поясненням геомітки.
- Пакет handoff і передача технічній команді.

### Не входить
- Програмна реалізація основного продукту (робить технічна команда).
- Фінальні тексти юридичних сторінок.
- Поети, архітектори та інші види мистецтва (наступні фази).

## 4. Вимоги до варіантів (що має бути представлено)

| Рішення (ID) | Обов'язковий зміст |
|---|---|
| `identity` | 3 напрями + V1; логотип, палітра, шрифти, приклад екрана карти й сторінки музиканта в кожному |
| `map.basemap` | Стиль карти для кожного напряму: суша, вода, дороги, підписи українською, контур України з Кримом, межі областей |
| `map.initial-view` | Уся Україна; варіант з підказкою «Біля мене». Початковий масштаб і поведінка deep link на область |
| `map.aggregation` | Від загального вигляду до окремих музикантів: кількість по областях → по містах → піни; плавне переміщення до центру обраної території; масштабування жестами і кнопками |
| `map.pin` | ≥ 3 варіанти піна музиканта; стани: з фото / без фото, зі звуком / без звуку, грає, обраний, натиснутий |
| `map.cluster` | Бульбашка з кількістю для області, міста, групи; великі числа («1,2 тис.») |
| `map.origin-notice` | Постійне й помітне пояснення, що геомітка — місце **походження**, а не поточного перебування; на карті, у картці, на сторінці |
| `audio.mobile-trigger` | Щонайменше 3 способи запуску випадкового фрагмента на телефоні без hover (`TAP_PREVIEW_AND_PLAY`, `TAP_PREVIEW_PLAY_BUTTON`, `LONG_PRESS_PLAY`) — з прототипом, який можна спробувати пальцем |
| `audio.desktop-hover` | Запуск при наведенні з затримкою наміру; відгук «грає» на піні; зупинка при знятті наведення |
| `audio.player` | Де керувати звуком (міні-панель / у картці); стан «звук заблоковано браузером» (D-23); стан «фрагмента немає» (D-27) |
| `musician.preview` | Картка з карти: ім'я, фото, місце походження, звук, лайк, перехід на сторінку |
| `musician.page` | Усі блоки: ім'я/назва, короткий опис, зображення, музичні матеріали, посилання на музику, YouTube-канал, місце походження (з поясненням геомітки), кнопка лайку, кількість лайків; атрибуція Вікіпедії та авторів фото |
| `like.button` | Кнопка і анімація для **необмежених** натискань (кожен тап +1, швидкі серії, великі числа) |
| `filters.region` | Фільтр за областю (27 регіонів, мультивибір, скидання, кількість результатів); розширюваність під нові критерії |
| `submission.form` | Поля з `02-contracts.md` 2.10: дані, посилання, завантаження 1–5 фото, автодоповнення міста; помилки; надсилання на повільному інтернеті; успіх |
| `nav.structure` | Як живуть разом карта, пошук, фільтр, сторінка музиканта, форма, «про проєкт» |
| `onboarding` | Перше відкриття: що це, як слухати, що означає позначка |

Для кожного рішення — mobile-версія обов'язкова, desktop — для ключових сценаріїв (карта, сторінка музиканта, форма).

## 5. Нефункціональні вимоги

- **Mobile-first**: опорний екран 390×844, мінімальний 360×640; цілі натискання ≥ 44×44 px; керування однією рукою.
- **Доступність**: WCAG 2.2 AA (контраст — розділ 5 контрактів; фокус; підписи для скрінрідерів; `prefers-reduced-motion`).
- **Технічна реалістичність**: варіанти враховують обмеження D-23 (звук лише після жесту), D-24 (на iOS немає
  плавного затухання), D-27 (більшість без звуку), фото є лише в третини музикантів.
- **Дані**: лише фікстури з `contracts/fixtures` (реальні музиканти з Вікіпедії) — ніяких «Lorem ipsum» і вигаданих імен.
- **Продуктивність студії**: варіант відкривається на середньому Android-телефоні за ≤ 3 с.
- **Доступ**: студія закрита паролем (basic auth); посилання передаються лише учасникам.

## 6. Формат фіксації рішень (відповідь на питання до виконавця)

1. Замовник у студії обирає варіанти → вони зберігаються як чернетка в його браузері.
2. Кнопка «Поділитися вибором» дає посилання з закодованим вибором → замовник надсилає його дизайн-ліду.
3. Дизайн-лід відкриває посилання, натискає «Затвердити» → студія формує `decisions.json` → дизайн-лід комітить його
   через pull request (історія: хто, коли, з якою приміткою).
4. Після затвердження всіх рішень команда `npm run handoff -w studio` генерує пакет `studio/handoff/`
   (рішення, токени, стиль карти, тексти, іконки, шрифти, скриншоти, `HANDOFF.md`).

## 7. Критерії приймання

Від замовника (протокол) — кожен перевіряється в студії:
- [ ] На платформі можна переглянути та порівняти запропоновані варіанти UX «Наші V2».
- [ ] На платформі можна вибрати й зафіксувати варіант айдентики та візуального стилю.
- [ ] Представлено UX інтерактивної карти України на мобільному та desktop-екрані.
- [ ] Представлено сценарій від загального вигляду карти до перегляду окремого музиканта.
- [ ] Представлено варіанти відображення музикантів як pin-маркерів.
- [ ] Представлено UX запуску випадкового аудіофрагмента музиканта з карти.
- [ ] Представлено сторінку музиканта з усіма переліченими інформаційними блоками.
- [ ] Представлено фільтрацію музикантів щонайменше за областю.
- [ ] Представлено форму додавання музиканта з полями для даних, посилань і зображень.
- [ ] В інтерфейсі присутнє пояснення, що геомітка позначає походження, а не поточне місцеперебування музиканта.
- [ ] Вибрані рішення можна передати технічній команді без повторного узгодження базових UX-сценаріїв.
- [ ] Ключові сценарії опрацьовані насамперед для мобільних телефонів, а також для desktop-екранів.

Технічні (перевіряє технічна команда при прийманні handoff):
- [ ] `decisions.json` відповідає схемі розділу 7 контрактів; усі рішення каталогу мають статус `APPROVED`.
- [ ] `tokens.json` містить усі токени розділу 5; тест контрастності проходить.
- [ ] `copy.uk.json` містить усі обов'язкові ключі розділу 8.
- [ ] `map-style.json` відкривається в MapLibre з плейсхолдерами тайлів, підписи українською, контур України з Кримом.
- [ ] Шрифти і іконки мають ліцензії, що дозволяють вебвикористання; ліцензії лежать поруч із файлами.
- [ ] Для кожного обраного варіанту є скриншоти mobile і desktop та опис поведінки в `HANDOFF.md` (стани, анімації з тривалостями, жести).

## 8. Відповіді на «Питання до виконавця»

| Питання | Відповідь |
|---|---|
| Оцінити терміни та вартість студії | ≈ 5 тижнів; трудомісткість у людино-днях за ролями — у плані, розділ «Оцінка». Вартість = людино-дні × ставки команди |
| Формат фіксації вибраних рішень | Розділ 6 цього ТЗ; схема — `02-contracts.md`, розділ 7 |
| Варіанти запуску аудіо на мобільному без hover | `TAP_PREVIEW_AND_PLAY`, `TAP_PREVIEW_PLAY_BUTTON`, `LONG_PRESS_PLAY` (D-25) — усі три як живі прототипи; рекомендація дизайн-команди — після тесту на 5+ людях |
| Що можна опрацьовувати незалежно від backend | Усе: студія працює на фікстурах `contracts/fixtures`, які мають ту саму форму, що й API (`02-contracts.md`, розділ 2). Залежність від backend лише одна — форма даних, і вона зафіксована контрактом |

## 9. Залежності та ризики

- Залежності: дані V1 (`wiki-dry-run.json` — уже в наявності), контракти (`02-contracts.md` — готові), доступ замовника до сесій погодження.
- Ризик «замовник не встигає обирати» → три демо-сесії з фіксованими датами (план, календар).
- Ризик «варіанти, яких продукт не вміє» → кожен варіант має `techId` або повний опис поведінки; варіанти поза колонкою «Технічні ID» узгоджуються з техлідом до показу замовнику.
- Ризик ліцензій шрифтів і фото → лише OFL/куплені шрифти; фото — з Commons з кредитами (як у фікстурах).
