# Реліз Nashi: інструкція для власника

Команди з `sudo`, `systemctl`, `journalctl` виконуються на сервері (через `ssh`). `ssh-keygen` і `git` на вашому комп'ютері.
Секретів у цьому файлі немає і бути не повинно.

Порядок дій: 1 SSH-ключ, 2 бекапи, 3 файл секретів, 4 реліз, 5 заміна ключів (ТІЛЬКИ після успішного релізу), 6 MapTiler, 7 імпорт, 8 перевірка. Відкат: розділ 9.

## 1. SSH-ключ для деплою

Причина збою деплою фронтенду: `ssh: handshake failed: ssh: unable to authenticate`. Сервер не приймає ключ із GitHub-секрету `VPS_SSH_KEY`.

1. На своєму комп'ютері створіть нову пару ключів (без пароля):
   ```
   ssh-keygen -t ed25519 -f ~/nashi_deploy_key -N "" -C "nashi-deploy"
   ```
2. Додайте публічну частину на сервер, у `~/.ssh/authorized_keys` користувача з `VPS_USER`:
   ```
   cat ~/nashi_deploy_key.pub
   ```
   Скопіюйте рядок і вставте його новим рядком у `~/.ssh/authorized_keys` на сервері.
   Права: `chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys`.
3. Приватну частину (весь вміст `~/nashi_deploy_key`, разом з рядками BEGIN/END) вставте в секрет `VPS_SSH_KEY`
   в обох репозиторіях: GitHub, Settings, Secrets and variables, Actions.
4. Перевірте `VPS_HOST` (адреса сервера) і `VPS_USER` в обох репозиторіях. Якщо ssh працює не на порту 22, додайте секрет `VPS_PORT`.
5. Перевірте ключ з комп'ютера: `ssh -i ~/nashi_deploy_key <користувач>@<сервер> echo ok`.
6. Після цього видаліть приватний ключ з комп'ютера: `rm ~/nashi_deploy_key`.

## 2. Бекапи Mongo

Бекапи не є частиною репозиторію. До релізу і до заміни ключів перевірте, що у вашому тарифі Mongo бекапи увімкнені.

## 3. Файл секретів на сервері

Зробіть це ДО першого деплою цієї гілки. Без файлу, або якщо в ньому бракує ключа, бекенд не запуститься після
`systemctl restart` (це простій), а деплой зупиниться ще до `git pull` з повідомленням.

Важливо: поки новий код не задеплоєно, працюючий бекенд бере секрети зі свого вбудованого `application.properties`.
Файл `/etc/nashi/...` на нього не впливає, тож тут нічого не міняйте, лише скопіюйте.

На сервері поточний checkout ще має старий `application.properties` з робочими значеннями. Скопіюйте його:
```
sudo mkdir -p /etc/nashi
systemctl show -p User --value nashi-backend
```
Остання команда показує користувача сервісу (порожньо означає root). Підставте його замість `<user>` (для root: `root`),
а групу дізнайтеся через `id -gn <user>` (підставте замість `<group>`):
```
sudo install -m 600 -o <user> -g <group> /var/www/nashi/nashi-backend/src/main/resources/application.properties /etc/nashi/nashi-backend.properties
```
`install` одразу створює файл з правами 600, тож він ніколи не читається іншими.

Перевірте, що всі сім ключів на місці (команда друкує лише назви, не значення):
```
for k in spring.data.mongodb.uri spring.ai.openai.api-key aws.s3.access-key-id aws.s3.secret-access-key telegram.bot-token telegram.admin-chat-id telegram.channel-id; do sudo grep -q "^$k=" /etc/nashi/nashi-backend.properties || echo "НЕМАЄ $k"; done
```
Тиша означає, що все гаразд. Якщо виведено `НЕМАЄ ...`, додайте ключ у файл (`sudo nano /etc/nashi/nashi-backend.properties`)
і запустіть перевірку ще раз. Таку саму перевірку робить і деплой.
Деплой робить її без `sudo`, від імені `VPS_USER`, тож цей користувач мусить могти читати файл: це root, власник
файлу (`<user>`) або, якщо дати групі право читання (`sudo chmod 640 /etc/nashi/nashi-backend.properties`), член групи `<group>`.

Також додайте CORS у цей файл, інакше дозволені всі origin (без cookies):
```
nashi.cors.allowed-origins=https://<ваш-домен>
```

## 4. Порядок релізу

1. До злиття перевірте checkout на сервері:
   ```
   cd /var/www/nashi/nashi-backend && git status --short
   ```
   Якщо там є змінений `src/main/resources/application.properties` (рядок ` M src/main/resources/application.properties`),
   поверніть його до версії з git, але лише ПІСЛЯ того, як файл секретів встановлено і перевірено (розділ 3): до того
   це єдина копія робочих значень.
   ```
   git checkout -- src/main/resources/application.properties
   ```
   Інакше `git pull` у деплої впаде на локальних змінах цього файлу.
2. Злийте бекенд (`feat/release-prep`) у `main`. Це запускає деплой.
3. Дивіться запуск у вкладці Actions репозиторію бекенду: спочатку `test`, потім `deploy`.
   Деплой чекає до 90 с (45 спроб по 2 с), поки `/api/v1/health` відповість 200. Якщо ні, він падає з написом `Backend did not become healthy`.
4. Переконайтеся, що health OK: `curl -i https://<домен>/api/v1/health` (або `localhost:8080` на сервері). Має бути 200.
5. Лише після цього злийте фронтенд у `main` (Actions: `check`, потім `deploy`).
6. Перевірте індекси в журналі:
   ```
   sudo journalctl -u nashi-backend | grep -i index
   ```
   Якщо індекс `slug_unique` не збудувався, у проді є дублі slug. Журнал назве проблему, дублі треба виправити.

## 5. Замінити ключі (тільки після успішного релізу)

Старі значення залишилися в історії git, тому їх треба замінити. Але робіть це лише після того, як новий бекенд
запущено з `/etc/nashi/nashi-backend.properties` і health дає 200 (розділ 4). Раніше не можна: старий працюючий код
читає вбудовані значення, і заміна ключа Mongo, AWS чи OpenAI зламала б його, а правка файлу в `/etc/nashi` нічого б не дала.

Для кожного ключа порядок такий: створити новий, вписати у файл, перезапустити, переконатися, що все працює, і лише тоді
вимкнути старий.

- OpenAI: створіть новий ключ у кабінеті. Старий видаліть після перевірки.
- AWS IAM: створіть новий access key для користувача S3. Старий деактивуйте (Deactivate) після перевірки, потім видаліть.
- MongoDB: створіть нового користувача бази з новим паролем (або змініть пароль) і оновіть `spring.data.mongodb.uri`. Старого вимкніть після перевірки.
- Telegram: у BotFather команда `/revoke`, оберіть бота, отримайте новий токен (старий перестає діяти одразу, тож вписуйте новий негайно).

Нові значення впишіть у `/etc/nashi/nashi-backend.properties` (`sudo nano /etc/nashi/nashi-backend.properties`), потім:
```
sudo systemctl restart nashi-backend
curl -i http://localhost:8080/api/v1/health
```
Очікується `200`. Значення нікуди не копіюйте і не надсилайте в чат.

## 6. MapTiler

Ключ MapTiler потрапляє в браузер, тому його треба обмежити. У кабінеті MapTiler відкрийте ключ і в Allowed HTTP origins
вкажіть домен сайту. Або створіть новий ключ з таким обмеженням і оновіть його у `.env` фронтенду на сервері
(`/var/www/nashi/nashi-frontend/.env`), а тоді перезберіть фронтенд (деплоєм).

## 7. Перший імпорт

У чаті адміна надішліть боту `/wiki_import`.

- Перший повний імпорт триває близько 6 годин: перелік кандидатів близько 15 хв, потім близько 2 с на виконавця
  (~15 тис. кандидатів), плюс близько 17 хв MusicBrainz.
- Прогрес не надсилається. Один звіт приходить у Telegram в кінці.
- Деплой або перезапуск `nashi-backend` під час цих ~6 годин зупиняє імпорт. Тоді після перезапуску надішліть `/wiki_import` знову
  (додаються лише ті виконавці, яких ще немає). Тому не мерджте і не змінюйте ключі, поки імпорт іде.
- Якщо у звіті сказано, що частина запитів кандидатів не вдалася (Wikidata була повільна), надішліть `/wiki_import`
  ще раз пізніше.
- Далі імпорт іде сам, щомісяця 1-го числа о 04:00 за Києвом.

Не імпортуються громадяни РФ та власники державних відзнак Російської Федерації (ордени, медалі, почесні звання,
державні премії). Радянські звання РРФСР, регіональні звання й відомчі медалі не враховуються.
Вибіркову перевірку робіть командами в чаті адміна:

- `/hide <slug або Q-id>` ховає опублікованого виконавця і не дає імпорту додати його знову (заявку на модерації
  він не чіпає: її відхиляють кнопкою в чаті);
- `/show <slug або Q-id>` повертає прихованого виконавця.

Старі кнопки approve/reject тепер працюють лише для заявок у статусі PENDING.

## 8. Перевірка після релізу

- [ ] Сайт відкривається, карта завантажується, піни видно.
- [ ] Фільтри (регіон, категорія, жанр) змінюють піни.
- [ ] Сторінка виконавця відкривається.
- [ ] Сторінка події відкривається.
- [ ] Радіо грає.
- [ ] `/?artist=<slug>` відкриває виконавця на карті.
- [ ] У консолі браузера немає помилок CORS.
- [ ] `/api/v1/health` повертає 200.

## 9. Відкат

Головне правило. Старий код (до цієї гілки) бере секрети з `application.properties`, а там лежать старі значення.
Після заміни ключів (розділ 5) вони відкликані, тож такий код запуститься з мертвими ключами. Тому:

- ДО заміни ключів можна відкотитися на будь-який попередній коміт.
- ПІСЛЯ заміни ключів відкотитися можна лише на коміт, який читає файл секретів, тобто на цю гілку або новіший.
  Не відкочуйтесь на старіші коміти і ніколи не повертайте секрети в репозиторій.

Як знайти останній робочий sha: у вкладці Actions репозиторію бекенду відкрийте останній зелений запуск `Deploy Backend`,
sha вказано біля нього. Або на сервері `cd /var/www/nashi/nashi-backend && git log --oneline -10`.

Варіант A (через git, з новим деплоєм). На своєму комп'ютері:
```
git checkout main && git pull
git revert <sha-проблемного-коміту>
git push origin main
```
Якщо це merge-коміт, додайте `-m 1`: `git revert -m 1 <sha-merge-коміту>`. Revert має лишати код, що читає файл секретів.

Варіант B (швидко, на сервері). Наступний деплой знову візьме `main`:
```
cd /var/www/nashi/nashi-backend
git checkout <останній-робочий-sha>
./gradlew clean build -x test
sudo systemctl restart nashi-backend
curl -i http://localhost:8080/api/v1/health
```
Коли проблему виправлено, поверніть сервер на гілку: `git checkout main` (інакше наступний `git pull` лишить checkout у detached HEAD).

Фронтенд так само, у `/var/www/nashi/nashi-frontend`: `git checkout <sha> && npm ci && npm run build && cp -r dist/* /var/www/nashi/frontend/`, а потім `git checkout main`.
