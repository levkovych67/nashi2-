# Імпорт артистів з Вікіпедії на карту НАШІ

Дата: 2026-11-04. Репозиторії: `nashi-backend` (імпорт), `nashi-frontend` (карта і сторінка артиста).

## Навіщо

НАШІ — карта української музики. Зараз артисти з'являються тільки через форму і модерацію в Telegram, тому їх мало.
Власник хоче, щоб на карті були **всі** українські музиканти, про яких є стаття в українській Вікіпедії: гурти й сольні
виконавці всіх епох — від композиторів XIX століття й оперних співаків до року і репу. Розбиратися, кого показувати,
будуть фільтри; фільтри розвиватимуть пізніше, окремим проєктом.

Успіх: після першого запуску на карті кілька тисяч нових артистів (≈4 тис. людей і колективів у базі), карта не гальмує, а кожен наступний запуск додає
тільки тих, кого ще немає, і нічого не дублює.

## Цілі

1. Механізм імпорту в бекенді, який збирає українських музикантів і гурти з Вікіданих та української Вікіпедії і
   записує в базу тих, кого там ще немає.
2. Повторний запуск не тягне вдруге вже імпортованих і не створює дублікатів артистів, доданих вручну.
3. Запуск раз на місяць автоматично і вручну — командою адміна в Telegram.
4. Усі імпортовані артисти з місцем в Україні видні на карті; карта групує близькі точки, щоб не гальмувати.
5. На сторінці імпортованого артиста є підпис джерела (вимога ліцензії Вікіпедії).

## Не робимо зараз

- Нові фільтри на карті (окремий проєкт). Наявні фільтри мають просто працювати з новими артистами.
- Оновлення вже імпортованих артистів, коли змінилася стаття (тільки додавання нових).
- Учасники гуртів, треки, альбоми, AI-теги для імпортованих (2,5 тис. викликів OpenAI — зайві витрати).
- Копіювання фото в наш S3.
- Адмін-панель.

## Чого не можна допустити (антицілі)

- **Пости в публічний Telegram-канал** про кожного імпортованого — 2,5 тис. постів. Звичайне схвалення
  (`approveArtist`) шле пост у канал, тому імпорт його не викликає.
- **2,5 тис. повідомлень на модерацію** в адмін-чат. Адмін отримує один звіт за запуск.
- **Дублікати**: той самий артист двічі, або вікі-копія артиста, якого вже додали вручну.
- **Запуск бекенду локально чи будь-які Spring-тести**, що піднімають контекст: `application.properties` містить
  бойовий токен Telegram і бойову адресу Mongo. Локальний запуск перехопить оновлення бойового бота, а тест-зріз
  Mongo без embedded-налаштування запише в бойову базу. Тільки чисті unit-тести без Spring-контексту.
- **Бан від Вікімедіа**: запити без User-Agent, паралельна злива запитів, ігнорування 429/503.
- Карта, що підвисає від 2,5 тис. DOM-маркерів.

## Обмеження

- Бекенд: Java 17, Spring Boot 3.4, MongoDB, Gson уже в залежностях. Нових бібліотек не треба: HTTP — `java.net.http.HttpClient`.
- Фронтенд: React 19 + react-map-gl/MapLibre, дизайн Frutiger Aero (`src/styles/aero.css`), `supercluster` уже в
  `package.json`, але не використовується.
- Деплой: push у `main` кожного репозиторію = деплой на прод. Зараз деплой зламаний (SSH-ключ). Пушити тільки з дозволу власника.
- Карта обмежена кордонами України (`maxBounds` у `MapContainer.tsx`), мінімальний зум 5,5.
- `swagger.json` однаковий в обох репозиторіях; типи фронтенду генеруються з нього (`npm run generate:types`).

## Як працює (вирішено)

### Джерела

- **Вікідані** (CC0) — факти: назва українською, тип (гурт/людина), місце, роки, жанри, фото, соцмережі.
- **Українська Вікіпедія** (CC BY-SA 4.0) — опис: вступ статті простим текстом.
- **Wikimedia Commons** — фото: URL мініатюри ≈400 px, автор і ліцензія для підпису.
- Тільки офіційні API (SPARQL `query.wikidata.org`, MediaWiki API), не розбір HTML.

### Хто потрапляє в імпорт

Обов'язково: є стаття в українській Вікіпедії.

- **Колективи**: екземпляр «музичний ансамбль» (Q2088357) або його підкласів — гурти, хори, оркестри, фольк-ансамблі
  (власник сказав «всіх митців») — і (країна походження — Україна, Q212, **або** місце заснування в Україні). Гуртів
  зараз ≈470; разом з хорами й оркестрами буде більше.
- **Люди** (рішення власника, 2026-11-04): людина (Q5); рід занять — музикант (Q639669), співак (Q177220) або
  композитор (Q36834), включно з підкласами; і (громадянство України, Q212, **або** місце народження в Україні —
  P19 → країна P17 = Q212); **крім** тих, хто має громадянство Росії (Q159, P27). Так потрапляють класики, яких
  Вікідані записують громадянами Російської імперії, Австро-Угорщини чи СРСР (Лисенко, Крушельницька), і не
  потрапляють ті, хто взяв громадянство РФ (Кобзон). Лише за коренем «музикант» це ≈3,8 тис.; зі співаками й
  композиторами — більше. Громадяни України ≈2,2 тис., народжені в Україні без громадянства України ≈1,9 тис., з них
  громадян РФ ≈185.

Важкі SPARQL-запити падають з 504 за 60 с, тому список збирається кількома легкими запитами (окремо по кожному кореню),
об'єднується за ID у коді, а деталі добираються пачками.

### «Вже зібраний» і дублікати

- Ключ — **ID у Вікіданих** (`Q…`), бо назва статті може змінитися. Новe поле `wikidataId` в `Artist`, унікальний
  розріджений індекс.
- Перед завантаженням деталей кандидат відкидається, якщо в базі вже є артист з тим самим `wikidataId`, **або** з тим
  самим `wikiTitle` (поле вже є — могло лишитися від давнього імпорту), **або** вручну доданий артист (без
  `wikidataId`, у будь-якому статусі, крім `REJECTED`) з тією самою назвою після нормалізації (регістр, лапки «»"",
  апострофи ' ’ ʼ, зайві пробіли). Вручну доданого артиста не чіпаємо, вікі-копію не створюємо.
- Двоє різних людей з Вікіпедії з однаковою назвою (різні `Q…`) — обидва імпортуються; другий отримує slug з `-q<номер>`.
- Повторний запуск коштує один-два SPARQL-запити на список; деталі тягнуться тільки для нових ID.

### Що записується в `Artist`

| Поле | Звідки |
|---|---|
| `name` | мітка українською (uk label); якщо немає — назва статті без уточнення в дужках |
| `wikidataId` (нове) | `Q…` |
| `wikiTitle` | назва статті в uk.wikipedia |
| `source` (нове) | `WIKIPEDIA`; для решти артистів поле порожнє = додані через форму |
| `biography` | вступ статті простим текстом |
| `style` | перший жанр (P136) українською, якщо є (текст для показу) |
| `musicTags` | усі жанри **англійською**, малими літерами — як теги, що вже є в базі від AI (`AiRequestService` просить англійські), щоб майбутні фільтри працювали з одним словником |
| `foundationYear` / `disbandYear` | гурт: P571 / P576; людина: початок / кінець діяльності P2031 / P2032, якщо є |
| `city` | мітка місця (див. нижче) українською |
| `region` | область місця (див. нижче) |
| `location` | координати місця (P625) |
| `imageKeys` | `[URL мініатюри з Commons]`, якщо є фото (наявний код віддає такий ключ як URL без S3) |
| `imageCredit` (нове) | автор, ліцензія і посилання на сторінку файла в Commons |
| `socialLinks` | офіційний сайт P856 → `WEBSITE`, Instagram P2003, Facebook P2013, YouTube P2397, Spotify P1902, SoundCloud P3040; плюс стаття Вікіпедії → `WIKI` |
| `status` | `APPROVED` одразу |
| `slug` | як зараз (з назви); якщо такий уже є — додати `-q<номер>` |

### Місце на карті

Карта показує тільки Україну, тому місце мусить бути в Україні:

- Гурт: місце заснування (P740).
- Людина: перше з місць — народження (P19), проживання (P551), роботи (P937) — яке лежить в Україні.
- «В Україні» = ланцюжок адміністративних одиниць (P131) доходить до однієї з областей, Києва, Севастополя чи АР Крим.
  Таблиця «ID області у Вікіданих → `Region`» (27 рядків; Київ → `KYIV`, Севастополь → `CRIMEA`) лежить у коді й
  перевіряється тестом.
- Немає такого місця або координат — артист зберігається без `location` і на карту не потрапляє (наявний запит карти
  вже відкидає `location = null`). Він доступний у списку артистів і пошуку.
- **Помилка, яку треба виправити**: `ArtistServiceImpl.toMinifiedDto` читає `getLocation().getY()` без перевірки на
  `null`, тож артист без місця зламав би список і пошук. Виправити з тестом.
- Список `/artists` сортується за `createdAt` (нові зверху), тож ≈2,5 тис. імпортованих опиняться над доданими вручну.
  Зараз не змінюємо — порядок і відбір у списку належать проєкту фільтрів.

Багато людей народилися в одному місті й отримають однакові координати (Київ — сотні). Зсув точок не робимо: це
розв'язує групування на карті та наявний список «У цій точці». (`GeoCoordinateService.adjustCoordinatesIfCollision`
зараз нічого не зсуває — повертає ту саму точку, хоч `CLAUDE.md` описує спіраль.)

### Індекси

`spring.data.mongodb.auto-index-creation` у проді не ввімкнено, тож `@Indexed` там не створює індексів. Унікальний
розріджений індекс на `wikidataId` створюється явно в `MongoIndexConfig`, як уже зроблено для `location`.

### Запуск

- **Раз на місяць**: 1-го числа о 04:00 за Києвом (`@Scheduled`, cron і вмикач у налаштуваннях; `@EnableScheduling`).
- **Вручну**: команда `/wiki_import` в адмін-чаті Telegram. Команди з інших чатів ігноруються. Зараз бот на будь-який
  текст відповідає «alive» — ця поведінка лишається для інших повідомлень.
- Одночасно працює тільки один імпорт; друга спроба отримує відповідь «імпорт уже йде».
- Імпорт іде у фоновому потоці, не блокує API.
- **Звіт** в адмін-чат після кожного запуску: скільки знайдено, скільки вже було, скільки додано, скільки без місця
  на карті, скільки помилок; при падінні — коротка причина.

### Чемність до Вікімедіа

User-Agent з назвою бота і посиланням на проєкт (без особистої пошти), запити послідовно, пауза між запитами,
повтор з затримкою на 429/503/504 (з урахуванням `Retry-After`), пачки по ≤50 назв для MediaWiki API.

### Перегляд без запису (dry run)

Збирач працює і без Spring: окрема точка входу (Gradle-задача) проганяє збір з реальних API і пише JSON-файл з
кандидатами, не торкаючись бази й Telegram. Так перевіряємо збір локально, а файл годиться для фейкового API фронтенду.

### API

- `ArtistViewDTO` отримує `source`, `wikiUrl` (посилання на статтю), `imageCredit` (автор, ліцензія, URL сторінки файла).
- `MapPinDTO` без змін.
- `swagger.json` в обох репозиторіях оновлюється, типи фронтенду перегенеровуються.

### Фронтенд

- **Групування на карті** (`supercluster`): на дрібному зумі — бульбашки з числом у стилі Aero (аква-гель), клік —
  наближення до рівня, де група розпадається. Окремі точки й однакові координати — як зараз (`StackMarker` і список
  «У цій точці: N»). Список має прокручуватися, бо в одній точці може бути кілька сотень людей.
- Рендеряться тільки маркери в межах екрана; при 2,7 тис. артистів карта лишається плавною на телефоні.
- **Сторінка артиста** з `source = WIKIPEDIA`: під описом — «Джерело: стаття „…“ з Вікіпедії, CC BY-SA 4.0» з
  посиланнями; під фото — «Фото: автор, ліцензія, Wikimedia Commons» з посиланням.

### Перевірка

- Бекенд: JUnit 5 без Spring-контексту. Розбір відповідей API — на записаних справжніх відповідях
  (`src/test/resources`); логіка дедуплікації й запису — з підробленим сховищем; таблиця областей — тестом.
- Живий прогін збору (dry run) локально → JSON → огляд кількості, областей, частки з координатами й фото.
- Фронтенд: `node:test` для групування; скриншоти карти на фейковому API, наповненому з dry run.
- Справжній перший імпорт — на сервері після деплою, командою `/wiki_import`.

## Залишено будівельнику

- Точні SPARQL-запити, розмір пачок, паузи, структура класів, назви налаштувань.
- Вигляд бульбашки групи в межах Aero.
- Як саме обрізати занадто довгий вступ статті (якщо обрізати — з «…» і посиланням на статтю).

## Рішення, які ухвалив я (власник може змінити)

1. Імпортовані артисти одразу схвалені, без модерації і без постів у канал.
2. Люди, в яких жодне місце не в Україні (частина діаспори), зберігаються, але не на карті — бо карта показує тільки
   Україну. (Раніше в чаті я пропонував ставити їх там, де народилися; це змінено через межі карти.)
3. Фото — посиланням на Commons, не копією в S3.
4. Ручний запуск — командою в адмін-чаті, а не HTTP-ендпойнтом: API без авторизації, ендпойнт міг би смикати будь-хто.
5. Без оновлення вже імпортованих артистів.
